# Architecture

## Components

| Piece | Role |
|---|---|
| **n8n** (Docker) | Scheduler and visual orchestration. Four workflows, each a short chain of Code nodes |
| **`src/` modules** | All real logic, unit-tested. Workflows embed a bundle of them (generated by `scripts/build_workflows.py`) |
| **Store port** | The Leads table. `LocalStore` (JSON file) or `SheetsStore` (Google Sheets REST). Chosen by `STORE_BACKEND` |
| **Mail port** | `DryRunMailer` (outbox files) or `GmailMailer` (Gmail REST). Chosen by `MAIL_BACKEND`. Sandbox rule lives here |
| **External services** | Gemini (LLM), Tavily/Serper (search), Hunter (optional emails), Jina Reader (company pages), Google DNS (MX check), Telegram |

## Workflows

| # | Trigger | Nodes | Does |
|---|---|---|---|
| 01 Telegram intake | every 20 s | Poll -> Handle & queue -> Send replies | Authorise chat, parse command, de-duplicate, add a `NEW` row, commit the Telegram offset |
| 02 Lead processor | every 1 min | Claim -> Enrich & pitch -> Save & send -> Notify | Adopt hand-typed rows, recover stuck rows, claim up to 2 leads, enrich, write back, send, notify |
| 03 Follow-up scheduler | every 1 min | Find due -> Reply check / follow up -> Notify | Cancel on reply, otherwise follow up in the same thread |
| 99 Error alerts | on failure of 01-03 | Error trigger -> Alert | Telegram message to the admin chat |

Telegram is polled rather than webhooked, so no public URL, tunnel or certificate is needed.

## The queue

The Leads table is the queue and the `status` column is the state machine.

```
            (typed in Sheet or sent in Telegram)
                          |
                         NEW ----------------------> DUPLICATE  (same company+city within the window)
                          |
                    PROCESSING  --(crash, >15 min)--> NEW, or FAILED after 3 attempts
                          |
      +-------------+-----+---------------+
      |             |                     |
  NOT_FOUND    NEEDS_REVIEW        READY_TO_SEND --(send ok)--> SENT --(due, no reply)--> FOLLOWED_UP
                    |  ^                  ^   |                  |
        human sets  |  | (send failed:    |   +-- retried next   +--(reply)--> REPLIED
        READY_TO_SEND  +--- stays here) --+       run, no new API calls
```

* A run claims at most 2 leads (`PROCESSING`) so overlapping runs cannot grab the same row and Gemini's per-minute limit is respected.
* `READY_TO_SEND` rows are retried **without** re-running search or the LLM, so a Gmail outage costs no quota.
* `NEEDS_REVIEW` is the human-in-the-loop exit: edit the row, set status `READY_TO_SEND`, and the next run sends it.

## Enrichment pipeline (`src/pipeline.js`)

1. **Resolve company -> domain.** Tavily search with aggregator sites (LinkedIn, Crunchbase, ...) excluded up front; retry once without the city; pick the result whose domain matches the company name (`strong`) or the first result (`weak`).
2. **Find people.** Two searches: LinkedIn result snippets and the open web.
3. **Extract candidates.** Gemini returns `{name, title, source_url}` as JSON. Code then drops any candidate whose full name does not literally appear in the fetched text, or whose `source_url` was not one of the fetched results.
4. **Rank.** Role score depends on company size: startups favour Founder, large companies favour Events/People. Roles scoring below 50 (e.g. "Head - Business Development") are not accepted as a contact.
5. **Find email.** Hunter (if keyed) -> an address on the company's contact page -> a role inbox such as `events@` -> a pattern guess (`first.last@domain`) accepted only if the domain has MX records. Source is recorded: `hunter | website | role_inbox | guessed`.
6. **Confidence.** Company match + named contact + email quality; guessed emails are capped at 0.7. Below `min_confidence` the lead goes to `NEEDS_REVIEW`.
7. **Pitch.** Gemini returns subject + exactly 3 lines + follow-up; validated; one retry; then a template.

## Data model

`sheet/Leads.csv` columns (the code and the CSV header are checked against each other by a test):
identity (`request_id`, `company`, `city`, `source`, `requested_by`), state (`status`, `attempts`, `updated_at`, `error`, `notes`),
result (`domain`, `company_summary`, `lead_name`, `lead_title`, `linkedin_url`, `email`, `email_source`, `confidence`, `sources`, `alt_contacts`),
outreach (`subject`, `pitch`, `followup_text`, `sent_at`, `followup_due_at`, `followup_sent_at`, `gmail_thread_id`, `reply_status`).

`Activity_log` is append-only (one line per pipeline step). `Config` holds runtime settings (sandbox mode, follow-up delay, confidence threshold, ...); values there override environment defaults, and a few internal keys (prefixed `_`, e.g. the Telegram offset) are hidden from config.
